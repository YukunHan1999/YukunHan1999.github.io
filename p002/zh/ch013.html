IO 控制器 ​

当具有不同需求的工作负载共享系统资源时，控制、限制和确定每个工作负载 IO 操作优先级的能力至关重要。

例如，我们需要确保当后台系统应用开始使用过量 IO 时，主工作负载不受影响，并确保系统能够灵活地将 IO 限制到低优先级工作负载，同时为高优先级工作负载提供 IO。

cgroup2 IO 控制器调节 IO 资源的分配，允许你指定某个 cgroup 每秒可读或写的 IO 操作数（IOPS）。它还允许你测量和监控 cgroup 的 IO 使用情况和 IO 压力。

cgroup2 IO 控制器增强 ​

cgroup2 IO 控制器相比版本 1 引入了诸多优势，极大地提升了系统上管理 IO 的能力。

cgroup1 仅统计和控制直接 IO，即文件系统元数据 IO（读和写）以及缓冲读。这使得其他类型的 IO，例如缓冲 IO（在许多用例中通常占大多数），无法被统计和控制。

cgroup2 允许对每个 cgroup 的所有 IO 进行全面控制和统计：缓冲 IO、文件系统元数据 IO、swap 和直接 IO，使 IO 控制成为资源利用策略中更加有效的组成部分。

接口文件 ​

与所有 cgroup 控制器一样，IO 控制器在启用时会在其子 cgroup 中创建一组对应的接口文件。你通过修改这些接口文件来调整和限制 IO。其他接口文件允许你查询和监控 cgroup 的 IO 统计信息。

以下是通常用于管理 IO 资源的配置文件。请务必参阅权威的 cgroup2 参考文档以获取更多细节。

文件描述
io.latency服务质量机制，用于保证 cgroup 的 IO 完成延迟水平。指定一个进程在获得其他进程的 IO 之前可以等待的毫秒数。

如果平均完成延迟长于此处设置的目标值，其他进程会被节流以提供更多 IO，从而有效地优先处理 io.latency 设置最低的作业。

io.latency 是目前首选的 IO 控制机制：详情请参阅下文关于 io.latency 的讨论。
io.pressure给出部分或全部任务等待块设备或 IO 的实际时间百分比。

详情请参阅 PSI 资源压力指标页面。
io.statIO 使用统计信息。

各行以 MAJ:MAJ:MIN 设备号为键，且不排序。定义了以下键：

  • rbytes: 读取字节数
  • wbytes: 写入字节数
  • dbytes: 丢弃字节数
  • rios: 读取 IO 的次数
  • wios: 写入 IO 的次数
  • dios: 丢弃 IO 的次数
一个读取示例的输出如下 :

8:16 rbytes=1459200 wbytes=314773504 rios=192 wios=353 dbytes=9973760 dios=79 8:0 rbytes=90430464 wbytes=299008000 rios=8950 wios=1252 dbytes=69632 dios=158
io.max在此指定 IO 限制。各行以 MAJ:MAJ:MIN 设备号为键，且不排序。

定义了以下嵌套键：

  • riops: 每秒最大读 IO 操作数
  • wiops: 每秒最大写 IO 操作数
  • rbps: 每秒最大读取字节数
  • wbps: 每秒最大写入字节数


写入时，可以按任意顺序指定任意数量的嵌套键值对。可以指定 max 来移除特定限制。如果同一键被多次指定，结果未定义。

BPS 和 IOPS 按每个 IO 方向分别测量，达到限制时 IO 会被延迟。允许临时突发。

为 8:16 设置读取限制为 2M BPS、写入限制为 120 IOPS：

echo "8:16 rbps=2097152 wiops=120" > io.max

读取返回以下内容：

8:16 rbps=2097152 wbps=max riops=max wiops=120

可以通过写入以下内容移除写 IOPS 限制：

echo "8:16 wiops=max" > io.max

现在读取返回以下内容：

8:16 rbps=2097152 wbps=max riops=max wiops=max

使用 io.latency 保护工作负载 ​

你通过指定延迟目标（例如 20ms）来使用 io.latency 保护工作负载。如果受保护工作负载经历的平均完成延迟长于其延迟目标值，控制器会节流任何延迟目标比受保护工作负载更宽松的对等 cgroup。

优先 cgroup 的目标与其他 cgroup 的目标之间的差值，用于确定其他 cgroup 被节流的力度：如果 io.latency 设置为 20ms 的 cgroup 被优先处理，则延迟目标 <= 20ms 的 cgroup 永远不会被节流，而目标为 50ms 的 cgroup 会比目标为 30ms 的 cgroup 被节流得更狠。

接口 ​

io.latency 的接口格式与其他控制器类似：

MAJOR:MINOR target=<目标时间，单位为微秒>

启用 io.latency 后，你会在 io.stat 中看到额外的统计信息：

  • depth=<整数>——该组当前的队列深度。

  • avg_lat=<时间，单位为微秒>——该组的运行平均 IO 延迟。这可以让你大致了解该工作负载在指定磁盘上可预期的总体延迟。

注意：所有 cgroup 参数都可以通过 systemd 配置。详情请参阅 systemd.resource-control 文档

使用 io.latency ​

这些限制仅应用于层级中的对等层级。这意味着在下图中，只有组 A、B 和 C 会相互影响，组 D 和 F 会相互影响。组 G 不会影响任何组。

因此，一种常见的配置方式是在组 A、B 和 C 中设置 io.latency

配置策略 ​

通常，你不希望设置低于设备所支持延迟的值。通过实验找到最适合你工作负载的值：从高于设备预期延迟的值开始，并观察工作负载组 io.stat 中的 avg_lat 值，以了解正常运行期间的延迟。以此值作为实际设置的基础：例如，尝试将其设置为 io.stat 中值高约 20% 左右。实验是关键，因为 avg_lat 是运行平均值，会受到统计异常的影响。

设置过于严格的控制（即延迟目标过低）会为工作负载提供更大的保护，但如果其他工作负载被过早节流，则可能以整体系统 IO 开销为代价。

另一个重要因素是硬盘 IO 延迟可能大幅波动：如果延迟目标过低，其他工作负载可能因正常延迟波动而被节流，同样会导致 IO 控制次优。

因此，在大多数情况下，你会希望将延迟目标设置得高于预期延迟，以避免不必要的节流——唯一的问题是高出多少。两种通用方法已被证明最为有效：

  1. 将 io.latency 设置为比通常预期延迟高 20-25%。这为工作负载提供了更严格的保护保证。然而，更严格的控制有时可能意味着系统在 IO 开销方面付出更多，从而导致系统整体 IO 利用率降低。这种设置对使用 SSD 的系统可能有效。

  2. 将 io.latency 设置为比通常预期延迟高数倍，尤其是对硬盘。 硬盘通常无争用时的完成延迟在 7 到 20ms 之间，但当发生争用时，完成延迟会迅速膨胀，很容易达到正常值的 10 倍。由于延迟波动如此之大，运行在硬盘上的工作负载通常对完成延迟的小幅波动不敏感；只有在延迟跃升数倍（这并不难触发）的极端情况下才会出问题。在这种情况下，可以通过为受保护组设置宽松目标（例如 50 或 75ms），并为较低优先级组设置更高的值（例如比高优先级组高 25ms），来实现有效保护。这样，工作负载可以获得合理的保护，而不会在没必要触发节流时显著损害硬盘利用率。

节流的工作原理 ​

io.latency 是工作守恒的：只要所有组都满足其延迟目标，控制器就不做任何事。一旦某个组开始未达到其目标，它就会开始节流任何目标比自身更高的对等组。这种节流有两种形式：

  • 队列深度节流——这是允许某个组拥有的未完成 IO 数量。控制器会相对快速地收紧，从无限制开始，一直降到一次只允许 1 个 IO。

  • 人为引入延迟——某些类型的 IO 无法在不负面影响更高优先级组的情况下被节流。这包括 swap 和元数据 IO。这些类型的 IO 允许正常发生，但它们会被“计入”发起它们的组。

一旦受影响组再次开始满足其延迟目标，它就会开始解除之前被节流的任何对等组的节流。如果受影响组只是停止执行 IO，全局计数器会适当地解除节流。

fbtax2 IO 控制器配置 ​

如前所述，fbtax2 cgroup 层级的目标是保护 workload.slice。除了内存控制器设置之外，团队发现 IO 保护对于让整套机制正常工作也是必要的。

当内存压力增加时，它通常会转化为 IO 压力。内存压力会导致页面逐出：内存压力越高，页面逐出和重新缺页就越多，因此 IO 也越多。要产生足够高的内存压力使磁盘 IO 饱和并不困难，尤其是 fbtax2 项目中机器所使用的旋转硬盘。

为了纠正这一点，团队使用了类似于上文策略 2的策略：他们通过将 workload.slice 的 io.latency 设置为高于预期值（50ms）来优先处理它。这为 workload.slice 提供了比 system.slice 更多的保护，后者的 io.latency 设置为 75ms。

当 workload.slice 因缺少 IO 而被延迟超过其 50ms 阈值时，它会获得 IO 优先级：内核限制来自 system.slice 的 IO，并将其重新分配给 workload.slice，以便主工作负载能够继续运行。

hostcritical.slice 被给予了与 workload.slice 相似级别的保护，因为那里的任何问题也可能影响主工作负载。在这种情况下，它使用 memory.min 来保证有足够资源保持运行。

尽管他们知道 system.slice 需要较低的 IO 优先级，团队还是通过反复试验确定了 75ms 这个数值，反复修改，直到在保护主工作负载和确保 system.slice 稳定性之间取得适当平衡。
