fbtax2：整合起来 ​

在这些文档中，我们介绍了一个贯穿始终的 fbtax2 项目案例研究，它说明了使用 cgroup2 及相关工具进行资源控制的关键原则。本页总结该策略，并提炼出可推广到各种用例和场景的原则。它还展示了测试结果，证明实施全面资源控制策略所带来的资源控制收益。

策略总结 ​

fbtax2 项目提供了一个可运行示范，展示了一个透明且全面的资源控制框架——将主工作负载与低优先级支持应用隔离并加以保护。

这个 fbtax2 示例也可以轻松扩展以覆盖各种其他场景，例如保护交互式工作负载免受旁加载批处理工作负载的影响，以及许多其他关键工作负载需要资源隔离的可能情况。

以下各节总结每个 cgroup 控制器及相关工具所使用的设置和策略，并展示 fbtax2 为 Facebook 数据中心带来的资源控制和利用率结果。

内存 ​

fbtax2 内存策略结合使用 memory.min 和 memory.low 进行内存保护。与 memory.high/memory.max 相比，它们具有以下优势：

  1. 它们是工作守恒的。不会因为资源限制而有内存闲置未用。

  2. 它们按比例调节内存回收。内存回收压力按超过给定 cgroup 的 memory.min/memory.low 保护量的比例分配。例如，如果两个对等 cgroup A 和 B 当前都处于 3G，但 A 有 2G 的 memory.low 保护而 B 没有，则 B 将承受三倍的回收压力。这使得 memory.min 和 memory.low 比 memory.high/memory.max 更容易使用且更有用，因为配置具有渐进效果，并且可以大致估算。

内存过量分配——为进程承诺比系统总内存更多的内存——也是 cgroup 内存控制的一项关键技术。尽管需求偶尔可能超过可用系统内存，但在一个系统上托管更多应用所带来的节省，超过了偶尔发生 OOM 情况的不利影响。

详情请参阅内存控制器策略页面。

Swap ​

正如 fbtax2 案例研究前一节 所讨论的，swap 在资源控制策略中可以发挥关键作用。

历史上，swap 一直被认为有问题，尤其是在硬盘上。但由于 oomd 使用 PSI 检测过多 IO 时间并在抖动或锁死发生之前介入杀死进程，swap 在此案例中被证明是有效的。

Swap 提供以下好处：

  • 更好地利用内存

  • 允许内存压力温和地积累，避免因突然尖峰而崩溃

如果不使用 swap，所有匿名内存都会被内存锁定。对于 fbtax2，除主工作负载外，所有地方都启用了 swap。

IO ​

io.latency 是用于 IO 保护的主要参数。通过 io.latency，你可以设置以毫秒为单位的目标延迟，该目标会定期与实际延迟进行比对，以确保实际延迟不被超过。如果实际延迟确实超过目标，其他 cgroup 的 IO 会受到约束，以将目标延迟降回来。

fbtax2 项目的实验表明，将 io.latency 设置为比通常预期延迟高数倍作为起点，尤其是对硬盘，能产生最佳结果。

io.latency 仅在 cgroup 层级的顶层 slice 上设置。高优先级 slice（例如 workload.slice）设为 50ms，低优先级 slice（例如 system.slice）设为 75ms，从而优先处理主工作负载。对于旋转磁盘，50ms 达到了一个良好平衡：低优先级 slice 不会受到过度惩罚，但当高优先级 slice 开始受损时仍能相当可靠地触发。低优先级值 75ms 决定当高优先级 cgroup 开始未达到目标延迟时，这些 slice 会受到多严重的惩罚。此设置不太敏感——60ms 或 100ms 也可能正常工作。

详情请参阅 IO 控制器 页面。

CPU ​

fbtax2 项目利用 Tupperware（Facebook 的内部容器化解决方案）上的 CPU 控制。每个 Tupperware 实例都启用了 CPU 控制器；这些设置确保 CPU 资源公平分配，并保证每个实例的 CPU 资源量。

每个实例的 CPU 设置在 cpu.weight 中配置，使用比例控制而非最大带宽限制（后者设置在 cpu.max 中）。

详情请参阅 CPU 控制器 页面。

cgroup2 层级 ​

该层级解决的主要目标是：

  • 防止非关键服务通过资源使用对关键服务产生负面影响。

  • 在机器无法维持名义工作负载时优雅降级。

  • 避免这些变更导致不必要的性能下降或高昂运维成本。

相关工具和组件 ​

以下各节讨论 PSI 指标和 oomd 在 fbtax2 策略中的作用。

PSI 指标 ​

PSI 指标在 fbtax2 资源控制策略中以多种不同身份发挥关键作用：

  • 提供关于给定工作负载是否有足够内存完成的洞察。

  • 提供关于系统总体内存使用的洞察，而不是使用反复试错的方法来确定有效内存设置。

  • 作为 oomd 杀死内存不足进程的触发器。

详情请参阅 PSI 压力指标页面 。

oomd ​

oomd 发挥三种作用.

  1. 以主动且上下文感知的方式解决内存过量分配情况（不要仅仅因为进程大就杀死它）。

  2. 为可重试的系统服务提供服务质量度量。如果发生严重抖动，最好杀死进程并让其重试，而不是延长痛苦。

  3. 在内核资源隔离开始失效时提供帮助。内核的资源隔离仍远非完美，在某些情况下无法充分保护主工作负载，例如由于某些锁构造导致的优先级反转。oomd 通过资源压力指标监控工作负载健康，并帮助理清这些情况。

fbtax2 测试结果 ​

以下各节展示当系统暴露于不同压力源时，上述战略决策的结果，并将 fbtax2 设置与基础设置进行比较。

system.slice 中的内存泄漏 ​

该图展示在 system.slice 中模拟内存泄漏的结果。这些测试模拟 system.slice 中的一个支持应用持续泄漏内存。一个 Python 脚本在其自己的服务中运行于 system.slice 下，并以不同速度持续分配内存，直到达到 20G。

10MB/s 增长模拟

  • 在 fbtax2 上，虽然每秒请求数（rps）有所下降，但内存和 IO 控制使主工作负载保持运行，最终 oomd 判断 system.slice 中的情况不可持续，杀死泄漏内存的服务，机器恢复。测试重复三次，结果大致相同。

  • 在基础设置上，第一次运行中内存消耗增长超过某一点后，机器进入深度抖动，不重启就永远无法恢复。

底部线条显示两台机器上 workload.slice 和 system.slice 的内存压力。在 fbtax2 上，虽然系统压力上升得明显更快，但 workload.slice 的压力在整个测试期间几乎不增加。在基础设置上，工作负载和系统压力一起上升，随后整个系统进入深度抖动。

fbtax2 的 rps 在压力期间出现多次锯齿状下降，主要是由于 oomd 基于 IO 压力选错了受害者，这只能暂时缓解问题。虽然这不关键，但我们应该能够通过更好地针对 IO 压力进行杀死来改进该行为。 50MB/s 增长模拟

50MB/s 增长的结果与 10MB/s 测试相同，只是时间加快。

  • 在 fbtax2 上，50MB/s 增长启动了三次。rps 受到一定影响，但资源控制支撑住了它，oomd 介入解决了情况。

  • 在基础设置上，50MB/s 增长启动一次。系统几乎立即进入深度抖动，不重启就永远无法恢复。

100MB/s 增长模拟

此图展示 100MB/s 增长：

  • 在 fbtax2 上，除了更深的停顿外，与之前相同——内存泄漏启动了三次，机器和工作负载基本完好地存活下来。

  • 在基础设置上，第一次运行时系统几乎立即进入深度抖动。这一次，hhvm 被内核 OOM 杀死，内存炸弹成功分配了 20G 并退出。机器随后缓慢恢复。

此测试模拟 system.slice 中的高 IO 负载。测试脚本解压三份内核源码树，对它们全部执行 touch，然后删除。

结果总结 ​

结果表明，当系统面临失控的资源问题时，fbtax2 与基础设置之间的差异非常显著。使用 fbtax2 时，发生的只是轻微临时服务质量下降。没有它，整个系统很容易丢失，需要长时间恢复。这种保护基本上没有成本——没有持续开销需要支付。

虽然保护很好，但 rps 仍有下降。它们来自：

  • 内核虚拟内存管理在不引发缺页的情况下无法知道哪些页面是热的。当没有内存压力时，内核会逐渐失去对当前工作集的了解。随着内存压力上升，内核必须通过换出页面然后让热页面重新建立自身来重建知识。这会导致即使是受保护工作负载也出现受控的尖峰。慢速硬盘会放大这种效应。

  • 硬盘速度慢且名义上超额订阅。换句话说，支持应用无法在不至少暂时影响 workload.slice 的情况下可接受地运行。资源保护配置必须允许这种波动。

  • 资源隔离并不完美。cgroup2 控制器具有固有和实现特定的限制，并且仍然存在剩余的优先级反转问题，可能将 system.slice 中的高资源压力转移到 workload.slice。

大多数要么直接由硬盘的慢速性能引起，要么被其大大放大。已经开始在配备 SSD 的机器上进行测试，下图展示了初步结果。

红色标记线是机器上启动的 50MB/s 内存泄漏。内存和 IO 保护在 SSD 上可以工作得好得多，并且几乎完美地在 workload.slice 和 system.slice 之间偏置内存和 IO 压力——前者保持在地板水平，而后者飙升。HHVM 几乎不受 system.slice 中内存泄漏的影响，只要 swap 空间可用，系统就能维持该状态。swap 耗尽时，oomd 介入并清理。
