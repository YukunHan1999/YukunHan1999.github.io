容器运行异构cpu架构 x86_64, aarch64, arm64, riscv64

binfmt_misc: 在内核层面进行模式匹配，当系统尝试执行一个文件时，如果标准格式（如 ELF）无法处理，内核会查询 binfmt_misc 的注册表，看是否有规则能识别它。
    注册: 用户通过向 /proc/sys/fs/binfmt_misc/register 文件写入特定格式的字符串来添加规则
    触发: 当一个文件被执行时，内核的 search_binary_handler() 函数会遍历规则。匹配成功后内核就会调用注册时指定的解释器, 并将要执行的文件作为参数传递给它。

fix-binary: 
    问题: binfmt_misc 的默认行为是“惰性打开”。这意味着，只有当内核真正遇到一个匹配的文件时，它才会根据解释器的路径去尝试打开它。如果解释器（如 qemu-aarch64-static）安装在宿主机上，而容器内没有这个文件，内核在容器的根文件系统（rootfs）中查找解释器时就会失败，导致“no such file or directory”错误?
    处理: 注册时即打开。当带有 F 标志的规则被注册时，内核会立即打开（open）指定的解释器文件，并持续保持这个文件描述符（file descriptor）处于打开状态，直到该规则被移除。执行时：直接使用已打开的句柄。当后续有文件触发该规则时，内核不再去文件系统中查找解释器，而是直接 exec 之前已经保持打开的那个文件描述符。

    binfmt_misc 是一个内核级的格式匹配与路由框架。而 fix-binary 标志通过将解释器的打开时机提前到规则注册阶段，并长期持有其文件描述符，巧妙地解决了在命名空间隔离（尤其是容器）环境下，解释器路径无法被正确解析的根本性矛盾。这使得宿主机上安装的 QEMU 静态模拟器能够无缝地为任何架构的容器提供服务。

宿主机支持:
    sudo pacman -S qemu-user-static qemu-user-static-binfmt
    sudo systemctl restart systemd-binfmt

验证:

总结:
    如果想在容器中运行异构的程序需要借助binfmt-misc+fix-binary的机制, 宿主机提供qemu-user解释器.
    运行异构的系统,需要容器中启动qemu-system-* 自己配置启动参数, 如果需要kvm能力, 需要容器启动时挂在--device /dev/kvm, 容器在这里只提供隔离环境.

    换角度思考透明执行异构程序 (binfmt-misc): 
        1. 容器中运行异构程序, 需要fix-binary
        2. 跨架构 chroot 环境, 不需要容器, 需要fix-binary
        3. 宿主机上直接透明运行异构程序或者其他格式的文件透明执行, 不需要fix-binary

CGROUP

你已经有源码和编译能力，这让你可以跳过单纯看文档的阶段，直接从可观测的行为和可修改的代码两端夹击。cgroup v2 的心智模型可以压缩成三件事：一棵树、每个节点挂着一组资源旋钮、进程挂在节点上。下面的实验设计就是围绕这个模型，从外部行为逐步深入到内核源码内部。

# 查询是否挂载cgroup
mount | grep cgroup2
stat -fc %T /sys/fs/cgroup/
cat /proc/filesystems | grep cgroup2

# 手动挂载 cgroup2, none 表示没有设备,内容由内核提供; 
# cgroup 在内核里面维护的是: 一组"进程分组" 的层级树 + 每组上挂载的控制器(cpu, memory, pids...)
mount -t cgroup2 none /sys/fs/cgroup

实验一：把 cgroup v2 文件系统“看穿”

目的：建立对“树 + 旋钮 + 进程归属”的直观感受，不碰代码。

操作：

  1. 确认挂载点：mount | grep cgroup2，确认 /sys/fs/cgroup 是唯一层级。

  2. 观察根节点：

    ls /sys/fs/cgroup/
cat /sys/fs/cgroup/cgroup.controllers
cat /sys/fs/cgroup/cgroup.subtree_control

    cgroup.controllers 列出当前系统所有可用的控制器（cpu、memory、pids、io 等）；cgroup.subtree_control 显示哪些控制器被下放给了子节点。

  3. 创建一个空 cgroup：

    mkdir /sys/fs/cgroup/lab
ls /sys/fs/cgroup/lab/

    你会看到 cgroup.controllers、cgroup.subtree_control、cgroup.procs 等核心文件，以及该节点已启用的控制器专属文件（如 pids.current、pids.max）。

  4. 观察进程归属：

    cat /proc/self/cgroup

    输出类似 0::/user.slice/...，这是当前 shell 所在的 cgroup 路径。每个进程有且仅有一个 cgroup 归属，由 task_struct 中的 css_set 指针最终指向。

源码锚点：kernel/cgroup/cgroup.c 中的 cgroup_init() 负责在启动时初始化根 cgroup 和所有控制器。读它的开头，你会看到 init_css_set 这个全局变量被加入哈希表，这是所有进程初始归属的起点。

实验二：用 pids 控制器“触碰”限制的边界

目的：选一个逻辑最简单、源码路径最短的控制器，完整走通“写旋钮 → 内核记账 → 触发限制 → 观察返回码”的闭环。pids 控制器是理想的起点，它不涉及复杂的资源回收或调度，核心逻辑清晰。

操作：

  1. 在 /sys/fs/cgroup/lab 下写入：

    echo 5 | tee /sys/fs/cgroup/lab/pids.max

  2. 把自己的 shell 移入该 cgroup：

    echo $$ | tee /sys/fs/cgroup/lab/cgroup.procs

  3. 尝试 fork：

     for i in $(seq 1 10); do sleep 100 & done

    你会看到在某个时刻 fork 失败，返回 Resource temporarily unavailable（EAGAIN）。这是因为 pids.current 触及了 pids.max，fork()/clone() 被内核拦截。

  4. 观察：

    cat /sys/fs/cgroup/lab/pids.current
cat /sys/fs/cgroup/lab/pids.events   # 看 max 事件计数

源码锚点：kernel/cgroup/pids.c。搜索 pids_try_charge 和 pids_can_fork，你会看到 pids.max 的写入如何设置 pids->max，以及每次 fork 时 pids_try_charge() 如何原子地增加计数并在超限时返回 -EAGAIN。这个文件通常只有几百行，非常适合作为第一个通读的控制器源码。

实验三：让 memory 控制器“杀死”一个进程

目的：观察 cgroup 的资源回收与 OOM 机制。memory 控制器比 pids 深得多，但它能让你看到 cgroup 如何与内核的内存管理子系统（memcg）深度耦合。

操作：

  1. 创建新的 cgroup（或复用 lab）：

    sudo mkdir /sys/fs/cgroup/memlab
echo 50M | sudo tee /sys/fs/cgroup/memlab/memory.max
echo $$ | sudo tee /sys/fs/cgroup/memlab/cgroup.procs

  2. 在另一个终端监控：

    watch -n 0.5 'cat /sys/fs/cgroup/memlab/memory.current'

  3. 在本 shell 中分配内存：

    python3 -c "a = bytearray(100*1024*1024)"

    你应该会看到进程被 OOM killer 终止，或分配失败。memory.current 在触及 memory.max 后会触发内存回收（reclaim），回收不足则调用 OOM killer。

  4. 观察 OOM 事件：

    cat /sys/fs/cgroup/memlab/memory.events

    oom 和 oom_kill 计数会增加。如果设置 memory.oom.group=1，整个 cgroup 的进程会被一起杀死。

源码锚点：mm/memcontrol.c。这个文件巨大，不要试图通读。聚焦搜索 memory_max_write 和 try_charge。memory.max 的写入最终设置 memcg->memory.max；而每次内存分配（page fault）路径上的 try_charge() 会在用量超过 memory.max 时触发 mem_cgroup_oom()。这就是“限制 → 记账 → 回收 → OOM”的完整链条在内核中的落点。

实验四：追踪“进程 → css_set → cgroup”的关联路径

目的：cgroup v2 的核心数据结构关联，是理解一切控制器如何生效的钥匙。你的目标是搞清楚：当把 $$ 写入 cgroup.procs 时，内核到底改了哪些指针。

源码阅读路径：

  1. 入口：kernel/cgroup/cgroup.c 中的 cgroup_procs_write() → __cgroup_procs_write()。这是 echo $$ > cgroup.procs 的内核入口。

  2. 关键函数：cgroup_migrate() / cgroup_migrate_execute()。进程迁移的核心不是直接改 task_struct->cgroups，而是通过 css_set 这个中间层。

  3. 数据结构：

    • struct css_set：一个不可变的快照，持有指向一组 cgroup_subsys_state 的指针数组 subsys[]。相同归属的进程共享同一个 css_set。
    • task_struct->cgroups 是一个 css_set 指针。
    • cgroup_subsys_state（css）是每个控制器在每个 cgroup 上的实例状态。memcg、cpu_cgroup 等都是 css 的嵌入或派生。

  4. 验证：用 drgn 或 crash attach 到运行中的内核，对当前 shell 的 task_struct 打印 task->cgroups，再打印 css_set->subsys[] 中每个 css 的 cgroup 指针，与 /proc/self/cgroup 的路径对照。

心智模型：task_struct → css_set → cgroup_subsys_state → cgroup。css_set 是共享的去重层：内核维护一个哈希表，相同 cgroup 组合的进程复用同一个 css_set，避免每个进程都持有一份冗余的控制器状态。

实验五：编译一个“会说话”的内核

目的：利用你的编译能力，在内核源码中插入观测点，让 cgroup 的关键路径主动“告诉你”它在做什么。这比被动读代码有效得多。

选项 A（最小侵入）：在 pids_try_charge 或 mem_cgroup_try_charge 的开头加一行 pr_info，打印当前 task->pid、css->cgroup->kn->name（cgroup 名称）和当前计数。编译、安装、启动，然后在实验二或实验三中触发路径，dmesg 会直接显示调用顺序和参数。

选项 B（观察初始化）：在 cgroup_init() 的循环中，对每个 ss->name 打印一行。启动后 dmesg | grep cgroup，你会看到每个控制器在启动时被初始化的顺序，以及 early_init 标志的区别。

选项 C（修改旋钮语义）：在 pids_can_fork() 中把 -EAGAIN 改成打印一条特殊日志再返回。这让你亲身体验“控制器代码如何决定用户态看到的行为”。

注意：修改内核后，务必用独立的构建目录（O=/path/to/build）编译，避免污染源码树。启动新内核时保留旧内核作为回退选项。

实验六：找到 Docker 容器在 cgroup 树中的“座位”

目的：把前面所有抽象落到你日常使用的容器上，完成从“实验 cgroup”到“真实系统”的闭环。

操作：

  1. 启动一个容器，让它持续运行：

    docker run --rm -d --name cglab --memory 100M alpine sleep 300

  2. 找到容器进程的 PID 和 cgroup 路径：

    docker inspect --format '{{.State.Pid}}' cglab
# 假设输出 12345
cat /proc/12345/cgroup

    你会看到类似 /system.slice/docker-<id>.scope 的路径（取决于你的 cgroup 驱动配置）。

  3. 进入对应的 cgroup 目录，观察 memory.max、cpu.max、pids.max 是否与你 docker run 的参数一致。--memory 100M 最终就落成了该目录下 memory.max 的值。

  4. 对比容器内 free -m 与 memory.current：free 看到的是宿主机全局视图（受 namespace 影响有限），而 cgroup 的 memory.current 才是容器真正被记账的用量。

建议的推进顺序

阶段实验目标源码焦点
1. 建立直觉实验一树、旋钮、归属cgroup_init()
2. 最短闭环实验二（pids）限制 → 记账 → 返回码kernel/cgroup/pids.c
3. 深度耦合实验三（memory）回收 → OOM → memcgmm/memcontrol.c 的 try_charge
4. 核心数据结构实验四task → css_set → csscgroup_migrate()、css_set 哈希
5. 主动观测实验五用 pr_info 让内核说话任意控制器路径
6. 回到现实实验六Docker 容器在树中的位置验证 docker run 参数的内核落点

从 pids 开始，是因为它的源码路径最短、反馈最直接；memory 和 cpu 的源码要深得多，建议在实验四把 css_set 和 cgroup_subsys_state 的关系搞清楚之后再进入。你的编译能力最有价值的用法是在实验五：不要只是读代码，让代码在运行时把关键路径打印出来，这样内核对你来说就不再是一个黑盒了。

什么是Vector, Victor?

     我们的缓冲器需要动态调整大小——当物品被添加时增加,当物品被带走时会缩小——因此我们需要一种特殊的数据结构。这正是 Rust 中的字符串在内部使用称为 Vector 或 Vec 的结构所管理的。字符串内部有一个 Vec<u8>——一个字节的向量,本质上是一个。正如我们在第3章中所看到的,u8代表无符号的8位数,其大小基本上是字节。因此,当你在操作字符串时,实际上是在处理一个字节的向量。
     此VEC不仅存储字节,还确保其保存的任何数据都可以以“&str”形式返回,该数据引用一组UTF-8编码的Unicode字符序列。Vecs 旨在高效管理内存。例如:如果在循环中初始化一个Vec并持续添加元素,那么一个简单的方法可能涉及为每个添加的添加器分配新的内存,每次将所有现有内存都转移到此新空间中。这将是低效的
    我们需要一种数据结构,当你添加和删除项目时,它可以随之增长和缩小。字符串在引擎盖下使用此类数据结构,以修改其所保存的文本。这种数据结构称为 Vector,VEC。一个字符串在内部维护一个 u8 的 Vec,这是一种简洁的表达方式:它使用 Vec 的灵活数据结构来容纳 u8,因此没有符号的 8 位数。那是一笔麻烦。因此,基本上,它是一个字节向量,而String数据结构可确保Vec保存任意数据点,最终在需要时你会得到一个&str,该数据也会指向内存中的字节,但这些数据可确保属于UTF-8编码的Unicode点的一部分。2
    内部Vec试图确保内存效率高。考虑创建新 Vec 并持续循环添加场景。在简单的实现中,Vec 会为所有旧项和新项分配一些内存,并将旧项复制过去,但在内部,Vecs 确保此类数据复制无需频繁发生。

理解编程中的内存管理?

计算机最小的内存单元是位数,表示为0或1。例如,正如我们之前所见,ASCII 字符 a 是 011001。为表示两个(aa),它们按顺序排列:011000010110001。了解每个角色的大小和起点至关重要,因为不同角色的位数可能相邻。

这就是指针的用处。它们像地图一样,指示数据的起始点和大小,使数据检索变得高效。考虑一个示例;指针只需要起始位置和一个字符的大小即可找到每个字符。

添加更多角色,比如aaa,并不简单。如果最后一个A的内存正在使用,你需要更多的空间。这需要从操作系统请求额外的内存以容纳新字符,然后复制到前面,然后添加下一个——这个过程比单纯使用可用内存更慢。

Rust 在编译器级别解决常见的内存管理挑战:
    它会阻止超出分配内存的写入。
    它能谨慎管理指针,以避免通过一个指针修改数据以及使用另一个指针访问过时数据等错误。
    Rust 的所有权模型(包括移动语义)可有效跟踪和管理指针,从而减少过时或相互冲突的数据访问中的错误。

与此相反,C语言需要手动内存管理,而Objective-C则使用参考计数(保留和释放)来管理内存。Java 和 JavaScript 采用垃圾收集器,可自动清理未引用的对象。

例如,JavaScript 使用字符串的指针数组,掩盖了开发人员的复杂性。尽管它以字符串数组的形式出现,但从技术上讲,它是指向字符串的指针数组,类似于 Rust 的 Vec<String>,但并未暴露底层指针。

继续我们讨论 Vecs 的内容,让我们来思考一下 Rust 的 Vec 如何处理数据:
如果每次将现有元素复制到新的内存位置,向 Vec 添加元素可能显得效率低下。相反,Vec 通过初始分配比当前所需的更多内存来优化此过程。这个额外的空间使Vec能够存储额外元素,而无需每次复制整个数组。只有当该容量得到充分利用时,才会分配更多空间并复制这些元素。因此,Vec 中的项数并不直接表示其使用的内存量;分配的内存通常超过当前需要,从而提升性能。该策略可平衡内存使用和处理效率。

example 1:

fn function_a() {
    function_b();
}

fn function_b() {
    function_c();
}

fn function_c() {
    println!("Inside function_c");
}

fn main() {
    function_a();
}

在此示例中,主调用函数_a,然后调用 function_b,从而导致函数_c输出一条消息。每个函数调用在调用栈上创建一个新帧,当每个函数完成后,其帧被移除,工作回到主帧。换句话说:当我们从main()转到function_c()时,堆栈会先通过一张纸来生成,描述main()的上下文,然后是function_a(),然后是function_b(),然后由println!生成的任何函数;在文本打印出来后,每张纸都逐一从堆栈中移除,直到我们返回main(),然后结束程序。

rust中使用panic!() 对于它不知道如何处理的错误。默认操作是开始解压堆栈,这意味着在重新向上链(或通过文件堆叠)进行清理。清理工作的一部分是打印出有关调用栈(在我们看来,它显示为一个堆栈跟踪)的信息,并处理变量和结构体。
或者,您也可以在发生恐慌时立即将 Rust 设置为求死执行,这可能会让程序变小,因为它会跳过展开。你在 Cargo.toml 中设置了这个,惊慌失措 = “流产”。这种方法速度更快,但要小心——可能会导致一些资源(如打开文件或网络连接)被挂断。
